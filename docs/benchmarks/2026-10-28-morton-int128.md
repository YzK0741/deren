# Morton encoding and Boost.Int128 benchmark, 2026-10-28

The Boost.Int128 mask/shift encoder is worth considering: on this machine it reduces complete
synthetic BVH make+destruction from 1.345 to 0.472 ms for 2909 uniform leaves, and from 1.134 to
0.375 ms for clustered leaves. These are CPU benchmark results, not renderer frame-time savings.
This benchmark was captured with production sources restored; the separate private adoption and
renderer-capture result is [recorded here](2026-10-28-private-morton-int128.md).

## Implementations

- `bit_loop`: the existing 32-iteration, three-axis encoder into `data_block<12>`.
- `boost_masks`: five shift/mask spreading stages per axis using `boost::int128::uint128`, followed
  by the same twelve little-endian output bytes.
- `native_masks`: identical spreading algorithm using the compiler's `__uint128_t`, as an algorithm
  control. It is not a portable production recommendation.

All arms preserve 32 input bits per axis, 96 output bits, the existing byte-lexicographic comparator,
and quantization scale 2^21, including the endpoint 1.0. No integer-order sort or 64-bit key change.
The actual project's `bvh<uint32_t>::make`, vessel allocator/deque, internal-node Morton computations,
and destruction are used. A temporary global selector chooses the encoder inside the normal
quantization function; all arms use this dispatch. Dispatch overhead is not separately calibrated.

Boost source: [official repository, pinned commit 16f0b3374470e3821c10277775de18cf320cda45](https://github.com/boostorg/int128/tree/16f0b3374470e3821c10277775de18cf320cda45).
It was downloaded only under `tmp/boost-int128-benchmark/`; the project's Boost.Graph subset is
unchanged. This tests that exact revision rather than promising behavior for another release.

## Method and correctness

AMD Ryzen 7 7745HX, Windows x86-64, MSYS2 Clang 23.1.3. Actual compile commands are retained:
the utility encoder object uses effective `-O2 -march=native` (an earlier `-O3` is overridden),
and the benchmark consumer uses `-O3`. Neither command enables LTO in this diagnostic configuration.
The possibility of dead-code elimination was addressed independently of LTO: every encoding
iteration publishes its output pointer through an inline-assembly memory-clobber barrier; every
BVH iteration publishes the tree before destruction. Hashing and membership checks occur outside
the timed regions. No build, unit test or renderer overlaps either timing process.

Two independent executions of the same frozen executable. Each case has one warmup round followed
by twelve recorded rounds; all six arm permutations occur twice, balancing every arm across first,
second and third position. Reported medians pool 24 samples; pooled min/max/means, per-process
medians and raw samples are also preserved. Inputs are repeatedly reused without cache flushing;
CPU frequency and affinity are not locked. This is a local benchmark, not a cross-platform survey.

Encoding uses 262144 points per batch, four complete iterations per timed sample. Inputs are fixed
seed full-32-bit and quantized-21-bit random coordinates, with the 2^21 endpoint explicitly included.
BVH data are deterministic uniform or eight-cluster synthetic AABBs. The 2909 case matches the
recent scene's leaf count only; these are not extracted Bistro world bounds. Full BVH samples use
32/8/1 builds for 2909/10000/100000 leaves respectively and include destruction. AABBs/IDs are
prepared before timing.

Sorting is a separate common control: actual `vessel::deque<bvh_node<uint32_t>>` records and actual
box-derived normalized keys, with construction/key generation excluded. It invokes the existing
comparator. Its CSV `bit_loop` label is a schema placeholder; no encoder runs in the sort timer,
and it is not an encoder-specific speedup. Do not add medians of separately timed phases to derive
an exact decomposition of full-build time.

Both executions passed:

- 524447 input triples against an independent branchless bit-by-bit oracle, all three encoders:
  axis bit positions 0-31, saturation, byte boundaries, normalized quantization endpoints, full32 and
  quantized random points. All twelve output bytes match.
- Identical sorted baseline/Boost keys; native output equality is checked before sorting as well.
- For every size/distribution/encoder, real BVH frustum-query membership matches direct AABB tests.
- Sorted-node output checks and checksums after timing. Both process checksums match.

The deliberately corrupted Boost output is rejected with `encoder mismatch` and exit code 2;
positive validation exits 0. This confirms the equality gate is active.

## Results

Encoding median ns per point, including the common public benchmark call/dispatch and output stores:

| Input | Existing bit loop | Boost masks | Native masks | Boost speedup over loop |
|---|---:|---:|---:|---:|
| Full 32-bit axes | 200.980 | 5.848 | 10.320 | 34.4x |
| Quantized 21-bit axes plus endpoint | 139.733 | 5.769 | 10.142 | 24.2x |

Complete BVH make+destruction median ms:

| Distribution | Leaves | Existing bit loop | Boost masks | Native masks |
|---|---:|---:|---:|---:|
| Uniform | 2909 | 1.345 | 0.472 | 0.510 |
| Clustered | 2909 | 1.134 | 0.375 | 0.414 |
| Uniform | 10000 | 4.547 | 1.778 | 1.954 |
| Clustered | 10000 | 4.031 | 1.702 | 1.825 |
| Uniform | 100000 | 50.220 | 21.664 | 23.326 |
| Clustered | 100000 | 44.614 | 20.889 | 22.471 |

At 2909 leaves, Boost reduces full make+destruction by about 65%/67% (2.85x/3.02x faster).
At 100000 leaves, the corresponding speedups are 2.32x/2.14x. The control shows much of the gain
comes from replacing the per-bit algorithm; adopting the same masks with native integers also
substantially improves these cases. Boost's advantage over native masks here is specific to this
implementation, compiler and target; it is not a general library-versus-built-in claim.

The 2909 uniform before/Boost medians are 1.347/0.464 ms in process one and 1.341/0.474 ms in process
two. Clustered medians are 1.129/0.373 and 1.139/0.376 ms. The result repeats across both processes.

Common precomputed-key node-sort medians, uniform/clustered: 0.101/0.100 ms at 2909 leaves,
0.613/0.621 ms at 10000, and 7.830/7.726 ms at 100000. These are reference costs rather than a
measured per-arm sorting improvement; output representation/comparison was held fixed.

## Scope and follow-up

This establishes an encoding and full-build opportunity. It does not measure renderer FPS, import
latency, scene mutation cost, query throughput, working-set memory, another compiler, or a real
animated scene. The paused-pose invalidation fix already removed repeated builds when transforms
are unchanged; faster encoding primarily helps initial construction and frames with actual scene
changes. A stationary object scene should not be expected to save this build cost every frame.

The private adoption retained the 96-bit storage/sort semantics and added permanent encoder
boundary/random tests; its animated-scene captures are in
[the production integration report](2026-10-28-private-morton-int128.md). Changing Morton comparison
order, reducing key width, removing internal-node codes or changing node allocation remains separate
work. The present benchmark does not mix those changes into the claimed gain.
