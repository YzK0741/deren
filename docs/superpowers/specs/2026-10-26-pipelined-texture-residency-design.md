# 准备与显示分离的纹理驻留流水线

状态：待用户审阅。2026-10-26。

## 已确认的意图

用户提出：一份相机状态的纹理已经准备完毕并用于渲染，另一份较新的相机状态用于可见性测试与纹理准备，以额外延迟和较高显存占用换取并行。

用户明确接受：准备超过一帧时继续显示上一份完整结果，允许延迟暂时增加。不能将准备延迟固定描述为“一帧”。本轮是方案设计，不实施优化。

## 为什么改变当前方案

当前同帧路径要求 visibility prefix 完成、CPU 读取反馈、纹理同步物化后才允许录制 suffix。诊断近景的 GPU 光栅关闭/开启约 19.35/19.31 ms，反馈约 0.075 ms；主机帧间隔却从 20.41 增至 32.71 ms。净增加的关键路径等待约 11.74 ms。移动时 lazy bind/上传路径平均约 6 ms，最慢样本约 159 ms。

目标是解除“显示必须等待最新输入对应的纹理”这一依赖，而非针对静止场景缓存。参考：`docs/benchmarks/2026-10-26-residency-bottleneck.md`。

## Approaches

1. 同帧精确反馈：保留最低延迟及精确需求，但存在已测出的串行等待；作为旧实现和诊断对照保留。
2. 双角色帧快照流水线（用户选择）：准备较新状态，显示最新完成状态；准备落后时重复旧完整结果。增加资源驻留和输入到显示延迟。
3. 固定下一帧截止：未就绪时阻塞或使用占位纹理。阻塞保留卡顿，占位不符合完整纹理的目标，不选。

“两个相机”是两个逻辑角色，不意味着只允许两个物理缓冲槽。实现必须避免旧视角再次完整光栅、同时为新视角额外光栅的双倍几何成本。

## 目标、边界与默认选择

- 持续移动相机和允许的场景变化均可工作；相机静止不是启用条件。
- 任意被显示的新场景输出，其需要的纹理已准备好；不以缺失纹理占位来掩盖准备落后。
- 准备、上传和显示使用非阻塞完成轮询；正常显示循环不等待候选帧的反馈或上传 fence。
- 不承诺 GPU 同时执行两个相机的光栅；即使单 graphics queue 也要恢复 CPU 与 GPU 的重叠。
- 不加入虚拟纹理、mip/page streaming、几何流送或相机预测。
- 保留现有关闭/同帧模式，新增显式选择的流水线模式；默认不变。配置拼写由实现者选择，不能静默改变旧模式的延迟语义。
- 本设计的槽数、过时任务处理、回退等为代理提出的实现默认值，并非用户逐项指定。

## 帧快照，而不只是相机矩阵

每个候选携带单调递增 request ID 和 scene generation，以及独立拥有的：

- 相机 view/projection、视口、渲染比例、裁剪参数及会改变可见性的配置；
- draw-item 到 material 的映射、对象变换、相关材质/纹理映射版本；
- 几何及其他 GPU 输入的强引用，必要时保留变形后的顶点/骨骼数据版本；
- visibility ID、depth、feedback、需求集合、纹理所有权、不可变资源绑定；
- 录制命令与完成标记、最终离屏颜色输出。

不得将反馈关联到已经更新的全局 draw-item 表，不得将旧可见性与新相机/新动画姿态混用。光照和后处理也使用该候选对应的输入版本。TAA/motion/history 按实际完成并显示的候选序列推进，重复旧输出不推进历史。

现有 `current_ubo`、`frame_visible`、visibility 资源和 descriptor heap 许多位置依附于当前 frame/swapchain image；必须明确区分准备槽、显示帧槽、swapchain image index。不得仅复制一个 camera 后继续共用这些可变状态。

## 调度与有限队列

默认使用三个候选快照槽，允许某份候选上传时 GPU 继续准备下一份可见性，避免将双角色实现为两个互相等待的任务。已显示的完整颜色输出独立保留；候选槽释放前须等待其所有 GPU/上传使用完成。

候选状态：Captured → VisibilityInFlight → FeedbackReady → Uploading → Renderable → ShadingInFlight → Complete。过时或失败候选进入 Retiring，完成在途工作后回收。

- 输入持续更新一个 latest-request mailbox，最多保存一个尚未开始的最新请求，不累计所有中间相机位置。
- 至多一个上传 batch 在途；其余槽可用于 visibility、shading 或退休。没有空槽时不阻塞显示，只更新 mailbox。
- 新请求覆盖尚未提交的旧请求。已提交的 GPU/host-copy 工作不可假定可以取消。
- 允许旧候选在新输入到达后继续完成并被显示：只要其 ID 比已显示结果新且 generation 仍有效。这避免连续运动造成永远没有候选完成。
- 在安全边界可以放弃尚未上传的过时候选，但不得连续抛弃所有进展；调度应始终保证一个选中的有效候选能够走到 Complete。已开始的上传不因每次输入更新而重新开始。
- 每次选择 ID 最新的 Complete 输出。显示 ID 单调递增，旧任务晚完成也不能使画面倒退。
- 没有更完整的新输出时，重用缓存颜色输出完成呈现，不重新完整渲染旧场景，更不重复光栅。

## 可见性结果复用与提交

每份候选只执行一次可见性光栅及反馈。反馈完成后异步上传所需纹理；Renderable 后直接利用保存的 ID/depth 和同一快照执行 resolve、lighting、post，不能再光栅一次。

准备提交使用独立 offscreen command buffer 与完成 token，不能将 acquired frame 的 borrowed recorder 交给 independent submission。现有 `command_submission` 支持独立 graphics submission；不将同步 `frame_checkpoint` 当作主循环中的准备接口。

显示仅采样已完成的离屏颜色图像，走轻量呈现路径。其 swapchain acquire/present 与候选准备完成互相独立，不能因新候选尚未完成而等待它。首次无任何完整输出时沿用加载画面。

跨 submission 的 ID/depth、feedback、纹理及颜色可见性需要显式依赖/资源状态交接。CPU 获知完成与 shader 访问安全必须分别建立，不能仅依赖一个布尔 ready。

## 纹理共享、绑定与回收

物理纹理按已有去重规则共享。A/B 共同需要的纹理不复制。准备新需求、正在 shading 的候选、已提交消费者及固定纹理均持有强引用或驻留租约。

需求不再等于“最新反馈集合”：只有没有任何快照/提交/上传持有租约的纹理才允许卸载；not_ready 仍是延迟回收，不能强制释放。

候选使用独立的 binding bank 或等价的不可变版本化资源表，shader 按快照选择资源表。不能让准备 B 的 descriptor publication 改写 A 正在读取的全局固定槽。共享物理图片可行，共享可变描述符状态不可行。

visibility/alpha-test 等准备阶段的先决纹理必须先驻留并被计入 pinned/保守需求。保留旧视角不意味着这些准备依赖可以使用缺失占位。

显存目标是活跃需求集合并集及在途引用，而不是复制两份完整资产。记录每槽需求、共有/独有 payload、实际 ready bytes、设备内存采样和延迟回收。

## 上传与线程边界

当前 lazy bind 同步执行物理资源创建和 host image copy，且上传使用 graphics queue、每张图片前后各提交并等待。不得仅把原有 frame-bound bind 放到线程池并宣称并行。

新增候选级显式 upload batch/job：接收拥有来源数据的纹理集合，返回可轮询的完成状态/错误；不依赖当前 acquired frame，也不调用其 recorder。主渲染线程不等待此 job。

默认一个专用上传 worker，可等待它自己的 batch fence；GPU queue 的 host 提交访问必须与渲染线程统一同步，等待期间不得持有 queue/global publication 锁。后台 worker 不修改 runtime 的 camera、frame_visible 或当前帧绑定。

优先将同批图片的上传前/后转换分别批量提交，保留 host image copy 的正确顺序；记录分配、转换提交/等待、host copy 各自成本。单 graphics queue 为首个支持路径，不强制要求额外 transfer queue。若引入其他 queue，另行建立 ownership/同步，不隐含支持。

物理图片可在上传线程准备，只有 job 成功且资源可见性满足后，才由快照所有者发布 Renderable 及其绑定。更早的帧绝不能观察到半发布状态。

## 场景变化、失败和退出

- 普通刚体变换可通过冻结变换/输入版本支持。动画/变形、透明、MASK、toon、RT 或其他消费者只有在其所有输入和需求可正确保留时才进入流水线；不能跟踪的场景明确回退原先全驻留渲染，不能悄悄当作静态场景。
- scene reload/material mapping 重建、resize、渲染尺度/路径改变增加 generation，旧候选不再接替新场景；旧已完成颜色可以暂时显示，候选资源等在途完成后回收。
- resize 可用保留的颜色图像做有边界检查的缩放呈现；颜色格式不兼容时使用加载画面，不以旧 swapchain 资源冒充新资源。resize/退出允许必要的生命周期 drain，正常帧不允许 wait_idle。
- 上传失败/OOM 保留最后完整输出，报告候选错误并采取有界重试/退避；不得无限分配更多槽、强制驱逐在途纹理或无限快速重试。设备丢失保留现有 fatal/恢复策略。
- 退出先停止接收请求，结束上传任务并等待各自完成，再回收队列、快照和资源所有者。

## 验收

1. 时序/状态测试：过时完成不回退显示 ID；输入快速变化仍有输出进展；mailbox、槽数、上传 batch 数有界；上传超过一帧时呈现线程继续工作。
2. GPU 正确性：同一冻结快照与 eager 参考相比，复用 ID/depth 的结果正确；首次显露不缺纹理；共有纹理只物化一次；候选 B 发布/回收不改坏 A；消费者未完成时不能重用槽。
3. resize、scene reload、模式切换、上传失败和退出时引用完整，validation 无错误。不能完整快照的消费者明确回退。
4. 历史：重复旧颜色不推进 TAA/HZB 历史，显示代际切换使用对应 camera/history；准备结果的历史和显示历史不混用。
5. 性能：沿用 Bistro 连续旋转及反复转身三轮对照，报告准备/完成/显示速率、候选丢弃数、重复呈现比例、request→display 的帧数及毫秒分布、GPU 各阶段、CPU 等待、上传分项和进程显存。
6. 不能用重复呈现形成的高 present FPS 作为渲染提速证据。必须分别统计每秒新完成画面数量和每秒呈现次数；每份候选只有一次 visibility raster。
7. 图像参考有已知非确定性，先记录同模式对照底噪，再设定并公开图像误差门槛；不能静默放宽此前严格比较失败的结果。

## 留给实现者的选择

具体类型/配置命名、完成 token 的存储、binding bank 的地址编码、批量上传内部接口、统计输出格式。若公共 RHI ABI 发生变化必须升级并检查兼容性。槽数三和上传 batch 数一作为首版限制，不自行扩展为无界队列。

实现前需要确认本设计；之后再编写分步实现计划。这里不承诺固定一帧延迟、不承诺上传可完全隐藏，也不承诺先前特定 FPS 数字能直接恢复。
