# HZB recovery CPU 录制剖析与优化

日期：2026-10-21。基线 `001e7ad9`；前一阶段记录：[camera recovery](2026-10-21-hzb-recovery.md)。本轮仅优化现有 CPU 录制路径，默认开关、RHI 接口、shader、图依赖与逐项绘制顺序均不改变。

## 定位与改动

临时计时分别覆盖候选扫描、并行规划（含等待）、发布、首次逐项录制、第二遍 replay、图描述和图 prepare。图 record 包含前述 item/replay 时间，不能重复相加。每个计时点累积60次报告一次，报告取每次启动最后一个完整窗口。

两遍路径的主要新增成本是约2,838–2,906项的第二遍 replay（约0.59–0.60 ms），不是图编译（约0.06 ms）。候选扫描与规划的绝对成本更大，但两组都执行，不是本次 recovery 增量的主要解释。

保留三处小改动：

1. 原始 push 不再创建 `shared_object::borrow` 控制块或复制到256字节 staging 数组，直接把已有 command buffer 和 byte span 交给同一个 `contract_push_heap_data`。保留256字节上限、offset=0、后端验证和失败返回。调用同步消费数据，旧 staging 数组原本也要求这个生命周期。
2. 首次录制与 replay 都只在相邻 item 的 cull mode 发生变化时设置状态。每次调用从未知状态开始，首项必发；不跨 pass 缓存、不重排 item，双面/单面材料切换保持原顺序。
3. 保存 recovery 独立 block 时设置 `pad=1`，replay 直接引用该副本，避免再次复制。第一遍 plan 和 push block 不变。

临时计时代码已从生产文件移除；`runtime.post_graph.cpp` 恢复到基线。没有增加常驻计时器、环境变量或新的渲染机制。

## 测量方法

RTX 4060 Laptop，Bistro geometry，1280×720，Release。near初始相机 `35,8,42,0,-88,0`，far为 `35,18,140,0,-83.071,0`；`--capture-sweep=0.02`，130帧。subtilis=true，沿用现有 host-cut 候选路径，不添加实验 builder 补丁。

每个代码版本、每个视点各3轮交错 OFF/ON，共24次启动。OFF为 **BUILD=1、CULL/RECOVERY关闭**，ON为BUILD+CULL+RECOVERY；validation/probe/TAA关闭。没有并发构建、测试或其他捕获。先测基线版本，再构建优化版本，逐项计时点相同；下表取每个启动最后完整60次调用窗口，再对3次启动取中位数。整帧 CPU 取同一启动最后60帧的 post+scene。窗口彼此可能错开少量帧，不能当成严格同帧分解。

未锁频，版本间也未交错重建，绝对时间和整帧变化包含机器波动。各项中位数分别计算，不保证各项之和等于总时间中位数；本轮不据 GPU 时间漂移宣称新的 GPU 收益。

## 结果（ms）

| 指标 | near 基线 | near 优化 | far 基线 | far 优化 |
|---|---:|---:|---:|---:|
| ON首次逐项录制 | 1.252 | 1.048 | 1.279 | 1.070 |
| ON第二遍 replay | 0.602 | 0.417 | 0.592 | 0.428 |
| ON图描述 | 0.203 | 0.203 | 0.212 | 0.208 |
| ON图 prepare | 0.056 | 0.057 | 0.062 | 0.061 |
| OFF post+scene | 4.70 | 4.43 | 4.60 | 4.42 |
| ON post+scene | 5.16 | 4.68 | 5.34 | 5.01 |
| ON−OFF post+scene | +0.46 | **+0.25** | +0.74 | **+0.59** |

第二遍 replay 的中位时间下降约 **30.7%（near）/27.7%（far）**；首次逐项录制也减少约0.20–0.21 ms。两遍路径的 CPU 改善与去除每项重复工作一致；build-only 对照也受首次录制优化影响，因此不能只报告 ON 的下降而忽略 OFF。

**0.2 ms预算仍未满足。** 本轮 post+scene增量中位数为+0.25/+0.59 ms，且replay单项仍约0.42 ms。它们仍不能替代规格要求的 `record_visibility_items` 内外精确验收；不把这一轮称作CPU预算闭环。后续若要继续降低 replay，应先测剩余 push/indirect 调用成本，再判断是否值得批量录制或改变逐项数据入口，本轮不引入这些机制。
